# Model Routing for Token Economics — How Spotify Cut 90% of Frontier Token Waste

---

## The Problem

Most of what an AI coding agent does isn't reasoning. It's I/O.

Reading five files to answer a question about one method. Generating a test file that follows the exact same pattern as the twenty test files next to it. Updating docs after a meeting. Thousands of tokens gone, almost zero reasoning. The seat license isn't what hurts — it's the tokens. And you're feeding all of it to a frontier model that's wildly overqualified.

The numbers make this concrete: by 2028, AI coding costs are expected to blow past the average developer salary (Gartner, June 2026). A quarter of engineering leaders already burn $200–$500 per developer per month on tokens. Some are well past $2,000. The tooling pays for itself — but only if you stop burning frontier tokens on work that doesn't need them.

Spotify's answer: two declarative modes and a plugin that enforces routing. No platform team. No new subscription. Mean token savings of **90%** on bulk reads.

## The Naive Approach and Why It Fails

The naive approach is what most teams do: write routing rules in a markdown file (like CLAUDE.md) and hope the agent follows them. "If the file is large, delegate to a cheaper model."

This fails in three specific ways:

**The rules are advisory, not enforced.** The agent can ignore them. There's no mechanism to block a frontier read when a cheaper read would suffice. The agent decides whether to follow the instruction, and often it doesn't — especially under context pressure when it defaults to the path of least resistance.

**Every project needs its own copy.** The routing rules aren't portable. Each repo needs its own version of the instructions, and they drift. What works for a Java monorepo doesn't apply to a Python microservice.

**No feedback loop.** The agent doesn't know how many tokens it saved or wasted. There's no signal to reinforce correct routing behavior.

## The Mechanism

Spotify built this on top of **AiKA Modes** in Portal by Spotify. A mode is a declarative agent that runs on an ephemeral runtime — think AWS Lambda, but for agents. You define instructions, pick a model, set parameters like temperature, and attach MCP tools. Portal handles the rest. No infra to manage, no API keys, no long-running servers.

### Two Modes

**Mode 1 — bulk-reader.** For when Claude would otherwise read multiple large files just to answer one question.

```yaml
name: bulk-reader
description: Bulk file reader for code analysis - delegates I/O from Claude Code
instructions: You are a precise code analyst. Read the provided files and answer
  the question concisely. Output structured bullets only. No greetings, no prose,
  no preambles. Lead every bullet with the exact name, type, or line number.
  Use nested bullets for details. Skip anything the caller did not ask for.
visibility: public
model: gemini-2.5-flash
resourceLimits:
  temperature: 0.2
tags:
  - coding
  - delegation
```

**Mode 2 — code-writer.** For tests, config scaffolding, type stubs, or anything where the output is predictable from existing patterns.

```yaml
name: code-writer
description: Boilerplate code generator - delegates output-heavy work from Claude Code
instructions: You generate code files based on a spec and reference files.
  Match the existing patterns, conventions, naming, and style exactly.
  Output only the code — no explanations, no markdown fences unless asked.
  If the spec is ambiguous, make reasonable choices that match the reference
  code's patterns.
visibility: public
model: gemini-2.5-flash
resourceLimits:
  temperature: 0.2
tags:
  - coding
  - delegation
```

That "output only the code" instruction matters. Without it, the model wraps everything in markdown fences and explanatory prose that Claude then has to parse through.

Both modes use Gemini 2.5 Flash as the worker in the examples, but the model field accepts any model you have configured. Pick whichever works for you.

### Three-Layer Enforcement

The routing is enforced by a Claude Code plugin called **shunt**, not by advisory markdown.

**Layer 1 — Hooks.** Claude Code hooks fire before every tool call. Shunt registers two PreToolUse hooks:

- **check-file-size** fires on every Read call. If the file exceeds a configurable line threshold (default: 350), the hook blocks the read and tells Claude to use the `/bulk-reader` skill instead. Targeted reads pass through — Claude already knows what section it needs.
- **check-bash-read** catches `cat`, `head`, `tail`, `less`, and `more` on large files. Piped commands (`cat file | grep`) pass through since those are targeted reads.

The threshold is configurable via the `SHUNT_MIN_LINES` environment variable:

```json
{
  "env": {
    "SHUNT_MIN_LINES": "500"
  }
}
```

**Layer 2 — Scripts.** Two bash scripts wrap the Portal CLI calls. Claude calls a script with named arguments. The scripts handle everything: building the request, invoking the actions, unwrapping errors, and reporting token usage to stderr.

Modes are addressed by name and resolved by Portal: case-insensitively, preferring your own mode, then your team's, then public ones. Fork the public `bulk-reader` into a customized version and yours automatically takes precedence — no configuration needed.

**bulk-read** wraps each file in XML tags for clear boundaries and sends them to the bulk-reader mode along with the question:

```bash
bulk-read --question "What does this service do?" --paths src/Service.java src/Handler.java
# Follow-up: ask again with the same paths
bulk-read --question "Which methods call the database?" --paths src/Service.java src/Handler.java
```

Every delegation is one shot. The invocation is ephemeral (nothing is stored server-side) and re-sending the files on a follow-up is free where it matters, because the corpus goes to the worker model and never enters Claude's context.

**code-write** sends a spec and a reference file to the code-writer mode, strips markdown fences from the output, and can write directly to disk. Claude never sees the generated code. The reference is required: without a file to match patterns against, the worker generates context-free code that fits nothing in your project.

```bash
code-write --spec "Write tests for UserService" --reference tests/OrderTest.java --target tests/UserTest.java
# Output to stdout
code-write --spec "Generate a config stub" --reference config/existing.yaml
```

**Layer 3 — Skills.** Two skill files (markdown with description and usage examples) tell Claude *when* and *how* to call the scripts. When the hook blocks a read, the block message points Claude to the `/bulk-reader` skill, which shows the exact invocation syntax.

This layering means the system degrades gracefully. Even if Claude doesn't read the skill description, the hook still blocks the expensive read. The skill just makes the redirect smoother.

### The Benchmarks

Tested against a Java monorepo across four scenarios, measuring tokens Claude would consume reading files directly vs. consuming the bulk-reader's summary or writing code via the code-writer. Mean bulk-read savings were around **90%**.

The code-write scenario is harder to measure in tokens because without shunt, Claude both reads the reference files *and* generates the output as expensive output tokens. With shunt, the code goes straight to disk — Claude never sees it.

### What Doesn't Work

**You can't delegate editing.** The worker model's summaries don't include reliable line numbers. If Claude needs to make edits based on the analysis, it still has to read the specific section directly. The hooks allow targeted reads (with offset/limit) for exactly this reason — delegation saves tokens on understanding, not on editing.

**You can't delegate reasoning.** The worker model found surface-level patterns but missed a subtle thread-safety bug in testing. Claude spotted it in seconds once given the right context. The routing explicitly excludes debugging, architectural decisions, and safety-critical code.

**Latency adds up.** Each delegation is a network round-trip: Claude Code → Portal backend → worker model → back. Responses typically take 10–30 seconds, and Portal caps a single invocation at 30 seconds. Very large generations need to be split into smaller calls. This is acceptable for large reads, but counterproductive for small ones — the line threshold exists for this reason, below it the overhead of delegation exceeds the savings.

### Why The Architecture Matters Beyond Token Savings

The plugin is a Claude Code artifact, but the idea underneath is model routing powered by AiKA modes. The modes are the load-bearing piece:

- **They're reusable.** The same bulk-reader and code-writer modes work across every project and every tool that can shell out to the Portal CLI.
- **They're shareable.** Both modes are public in AiKA. Anyone can use them without creating their own.
- **They're composable.** You could create a doc-writer mode for documentation, a reviewer mode for code review summaries, a translator mode for i18n. Each is a few clicks away.
- **They decouple the routing decision from the worker.** The plugin decides *when* to delegate. The mode decides *how* to respond. Swap Gemini Flash for a cheaper model, change the system prompt, add MCP tools — the plugin doesn't change.

This turns model routing from a systems engineering problem into a configuration problem. You don't build infrastructure. You describe what you want and name it.

## What This Means for the Systems You Build

If you're running any AI coding agent on a codebase — Claude Code, Codex, Cursor, anything — you're almost certainly burning frontier tokens on reads and boilerplate generation. The 90% savings on bulk reads is specific to Spotify's Java monorepo benchmark, but the principle generalizes: most agent I/O is pattern-matching against existing code, not reasoning.

The line threshold (350 lines default, configurable) is the key design decision. Below it, the network round-trip overhead exceeds the token savings. Above it, delegation pays for itself. This threshold will be different for every team — it depends on average file size, network latency to your worker model provider, and the ratio of read-heavy vs. reasoning-heavy tasks.

The hook-based enforcement is what makes this production-grade instead of demo-grade. Advisory routing instructions in a markdown file are exactly the kind of harness failure described in the harness engineering concepts from previous readings — the agent ignores advice when it's convenient.

## The AI-Era Connection

**Multi-model routing.** This is the most direct implementation of the router pattern from graph engineering. The hook classifies work (large file read? boilerplate generation?) and routes to the appropriate model. The classification is deterministic (line count), not LLM-based, which avoids the cost of classifying every call.

**Semantic caching analog.** Every delegation is one-shot and ephemeral — nothing is stored server-side. But the pattern enables caching at the mode level: if you wanted to cache bulk-reader responses for the same file+question pair, the mode architecture supports it without changing the plugin.

**Token budget enforcement.** The hook enforces a token budget by blocking expensive operations before they happen. This is proactive rate limiting on token consumption, not reactive billing alerts after the fact.

**RAG pipeline applicability.** If you're building a RAG system that reads many documents to answer one question, the same routing principle applies. Use a cheap model to extract and summarize from documents. Use the expensive model to reason over the summaries. The boundary is the same: I/O vs. judgment.

## How This Connects

This is the most immediately practical concept in this file. The harness engineering insight — that the environment around the model matters more than the model itself — manifests here as: the routing infrastructure around the frontier model determines whether you spend $200/month or $2,000/month on tokens for the same work quality. The Netflix GenRec paper (next section) applies the same principle at infrastructure scale, routing different parts of the recommendation pipeline to different model sizes and optimizing context length to control cost.

## The Mentor's Honest Take

The mistake you will make: you will think "I should build something like this" and start designing a general-purpose model routing framework. Don't. Spotify built exactly two modes — bulk-reader and code-writer — and enforced routing with a line-count threshold. That's it. The complexity ceiling is deliberately low.

The non-obvious implication: the line threshold is doing more work than it looks. It's not just a cost optimization — it's a quality boundary. Below the threshold, the frontier model's context window can hold the file and reason about it effectively. Above the threshold, the frontier model's attention is diluted across thousands of tokens of irrelevant code, and the cheap model's focused summary actually produces *better* input for the reasoning step. You're not just saving tokens — in some cases you're getting better results by routing the read away from the frontier model.

Here's what matters for your background specifically: you're building RAG systems. Your retrieval pipeline reads many documents to synthesize one answer. Right now, every document goes to the same model at the same cost. The Spotify pattern says: use a cheap model to read and extract, use the expensive model to reason and synthesize. The boundary is the same — I/O vs. judgment — and the savings should be comparable.

**Ranking: Essential.** This is not background knowledge. If you're paying for frontier tokens in any agentic workflow, this directly reduces your costs by up to 90% on the I/O portion. The implementation is simple enough to ship in a day. The principle (route by work type, not by task) applies to every multi-model system you'll build.

# Netflix GenRec — Replacing Feature Engineering with Context Engineering at Recommendation Scale

---

## The Problem

Netflix's recommendation system serves hundreds of millions of members across movies, series, games, live events, and podcasts. The current production system generates personalized recommendations using a large number of hand-crafted features spanning user, item, and interaction signals, with extensive higher-order feature interactions and customized architectures tailored to different recommendation needs — specialized networks for feature interactions, transformer-based architectures for dynamic interests, multi-task learning setups.

This has iterated over many years and works. The problem is what happens next. Onboarding a new content type or recommendation surface requires substantial work in feature engineering, model architecture design, infrastructure changes, and experimentation. The system's complexity makes it difficult to keep pace with business growth.

Out-of-the-box LLMs are also not the answer. They over-recommend globally popular content, hallucinate out-of-catalog titles, ignore business constraints, and offer limited personalization.

GenRec is Netflix's attempt to bridge the gap: an LLM-backed recommendation ranker built on top of an in-house foundational LLM, designed to replace feature engineering with context engineering while meeting production cost constraints.

## The Mechanism

### Two-Phase Training Framework

**Phase 1 — Foundation.** An open-source LLM is adapted to Netflix data to build deep understanding of the catalog and member behavior. This phase optimizes broad capabilities: world knowledge, personalization, content understanding, language capability. It runs at low cadence — the foundation doesn't change frequently.

**Phase 2 — Post-Training.** This foundation model gets further trained on recommendation-ranking-specific data, labels, and reward signals. Phase 2 focuses specifically on ranking quality and recommendation steering. It updates more frequently to track new content launches, evolving popularity patterns, and members' latest interests. And it must be explicitly cost-efficient because it serves large-scale traffic directly.

The key difference: Phase 1 aims for the most capable foundational model with less constraint on serving cost. Phase 2 must be cost-efficient while maintaining quality on fresh data.

### Post-Training Data: Conversations, Not Features

Members generate hundreds of billions of interaction events across diverse content types. GenRec transforms a member's historical interaction data into a single-turn or multi-turn "conversation" between a user and a recommender. Each conversation contains:

- **Context:** surface, time, device, locale
- **User profile & history:** country, tenure, plan, historical interactions
- **Item-level detail:** item IDs, metadata (title name, release time, synopsis), popularity trends
- **Task:** e.g., predict the next items the user will play or thumb up
- **Assistant message:** the user's actual feedback (play, play duration, abandon, thumb) — this is the ground-truth signal

The LLM is optimized on this conversational data to model how assistant messages depend on preceding user messages.

### Input Verbalization and Context Engineering

Unlike traditional recommenders that encode interactions into hand-crafted features or dense embeddings, GenRec verbalizes rich user interaction histories as natural language or lightly structured text. The LLM learns higher-level patterns — item relationships, temporal dynamics, evolving interests — directly from raw input text, rather than encoding these through manual feature engineering.

This is not merely converting signals into text. It requires deliberate context engineering to accommodate long user context under a finite token budget. A member's history can easily exceed the token budget due to sheer volume of interactions and richness of per-interaction metadata. The context window is a limited, valuable resource — excessively long contexts dilute attention and increase costs.

The curation strategy:

- **Retain in full:** high-signal engagements like long-duration plays and thumbs-up — verbalized with richer metadata
- **Omit entirely:** recent low-signal events like very short plays or noisy clicks — they contribute little relative to their token cost
- **Summarize or compress:** repetitive behaviors like binge-watching sessions — compressed instead of listing every event
- **Elaborate selectively:** important items (new releases, cold-start items) get more detailed metadata to compensate for limited information from history

Short- to medium-term history gets higher granularity. Older history is omitted or compressed into a brief user-interest summary. The goal: a compact set of highly informative tokens that preserves recommendation quality without exceeding the context window or blowing up inference costs.

### Post-Training Objective

GenRec Phase-2 training combines two main objectives:

**Recommendation ranking objective.** A catalog-aware ranking objective that trains the model to assign higher scores to items matching high-value engagements (long plays, strong explicit feedback). Positive labels use denoising logic and thresholds that vary by content type. These labels feed a cross-entropy loss over the item catalog, teaching the model to produce quality ordering given the verbalized context.

**Language modeling objective.** Standard next-token prediction over verbalized inputs and outputs (predicted titles, textual fields). This maintains the backbone's language understanding and text generation capabilities, important for: (i) modeling rich natural-language histories and metadata, (ii) enabling recommendation steering via prompts, and (iii) keeping open future text generation use cases like natural-language explanations.

The overall loss:

```
L = α · L_ranking + β · L_language + γ · L_miscellaneous
s.t. α + β + γ = 1, α, β, γ ≥ 0
```

During inference, only the ranking task generates recommendations. The language modeling objective primarily serves to improve the ranking task through complementary textual information and preserve language understanding.

### Model Architecture

GenRec's backbone: a decoder-only Transformer with next-token-prediction style training, augmented with a **catalog-aware ranking head** that constrains recommendations to in-catalog items and supports efficient scoring over large candidate sets.

Scoring happens in three stages:

1. **Verbalization.** A verbalizer maps interaction history, context, and item metadata into a single text sequence.
2. **Pooled representation.** The LLM encodes this into a d-dimensional representation (hidden state at a pooling position) summarizing user preference and context.
3. **Catalog-aware scoring.** A scoring head assigns each item a score by combining the pooled representation with a learned d-dimensional embedding per item.

The LLM weights, scoring head, and item embeddings are trained jointly. A softmax over the catalog converts scores into a probability distribution for ranking. When the catalog is too large, sampled-softmax is used instead.

### Reward Signals

Beyond raw accuracy, GenRec must satisfy business requirements (content mixing — balance across movies, shows, live, games, podcasts) and maximize long-term member satisfaction rather than short-term engagement.

Two categories of rewards:

**Long-term satisfaction proxies.** These estimate how strongly a short-term engagement correlates with long-term outcomes. Because true long-term metrics are noisy and delayed, they use more stable proxies learned from historical data. Higher values go to engagements encouraging return visits, broader catalog exploration, or sustained engagement over time.

**Behavior rebalancing.** Additional rewards rebalance behavior across content types (movies vs. games vs. live vs. podcast) and launch stage (pre-launch, newly launched, evergreen) to meet business objectives like exposure fairness.

These are integrated via a **reward-weighted ranking loss**: each training example gets a scalar weight derived from multiple reward signals, and the ranking loss is scaled accordingly. High-value engagements get larger weights, low-value behaviors are down-weighted.

This is simpler than full RL. In preliminary experiments, GRPO showed additional gains over supervised finetuning, but the training overhead makes it better suited for future work. The reward-weighted loss is the main alignment mechanism due to simplicity, stability, and cost.

### Online Serving and Cost Optimizations

GenRec is served on Netflix's internal LLM serving stack using vLLM. At Netflix scale, serving cost is a first-class constraint. Inference cost is roughly proportional to `model_size × context_length`. Two complementary strategies:

**Smaller and distilled models.** Trained on larger or more targeted datasets, aiming to recover quality of larger models while reducing per-request computation.

**Context length optimization via verbalization compaction.** The context experiments showed context can be reduced to roughly **a third** of the original token budget (from ~5,000 tokens down to ~1,700) with negligible degradation in offline ranking quality. Since GenRec is largely compute-bound with serving cost approximately proportional to context length, serving cost is also reduced to roughly a third.

**Prefill-only inference.** Since GenRec needs to rank items over a large candidate set, naïve autoregressive decoding (token by token, beam search) would be prohibitively expensive. Even though the backbone is a generative, decoder-only LLM capable of autoregressive decoding, GenRec deploys in a **prefill-only configuration**: the model consumes the input context once and produces ranks for the full candidate set in a single forward pass. No step-by-step decoding.

### Experimental Results

**GenRec vs. Production Baseline.** With about **40× less** Phase-2 labeled training examples than the production model, GenRec achieves an offline lift of approximately **+1.6% relative in MRR** over the baseline. Offline metrics continue improving as training data and input signals scale up.

Online A/B test: ~10% of Netflix traffic for 4 weeks. Under a low-data, low-signals configuration, GenRec achieved statistically significant improvements on both short-term and long-term online metrics. Specifically:
- Short-term homepage engagement: **+0.115%** (p = 3.1 × 10⁻¹⁰)
- Long-term core metric: **+0.006%** (p = 0.025)

These relative lifts are small in absolute value but at Netflix scale they correspond to substantial aggregate effects.

**Data Scaling.** Holding other variables fixed, training on datasets from 1× to 20× the smallest configuration. For both ~1B and ~10B parameter models, offline MRR improves monotonically as Phase-2 data increases. The ~1B model has lower absolute MRR but exhibits a similar scaling pattern to ~10B.

**Model Scaling.** Under a fixed training budget (same GPU config, similar wall-clock training time), larger backbones (~1B to ~10B) consistently achieve higher offline MRR.

**Quality-Cost Tradeoff.** Data and model scaling both improve quality but increase costs — especially important for a model trained at higher cadence and directly serving large-scale traffic. Netflix explicitly searches for "sweet spots" on the quality-cost Pareto frontier: large enough for most incremental quality gains, small enough that post-training and serving stay within budget.

**Impact of Phase 1 vs. Phase 2:**

| Phase | Impact |
|-------|--------|
| Phase 1 (foundation) | +10-20% MRR vs. using an off-the-shelf LLM |
| Phase 2 (post-training, at Phase-1 cutoff date) | +35-50% MRR gain over Phase 1 alone |
| Phase 2 (after 2 weeks of staleness) | Gain rises to ~80%, reflecting growing staleness of the less-frequently-updated Phase-1 backbone |

### The Paradigm Shift: Six Ways LLM-Native Recommendations Differ

**1. Feature engineering → Context engineering.** The "prompt" becomes the new feature vector. Modeling effort shifts from designing individual features to context engineering: deciding which signals to include, how to summarize them, how far back in time to go, how to encode them within a token budget.

**2. Customized architectures → Foundation backbones.** Instead of two-tower models, DLRM-style networks, custom attention blocks — standardize on transformer backbones inherited from a foundation model. Innovation moves up: from per-task architecture design to data, scaling laws, post-training strategy, and inference optimization.

**3. Scaling laws as a design guide.** Classical RecSys stacks hit diminishing returns due to sparse IDs and heavily engineered objectives. LLM-backed systems inherit pre-trained scaling behavior. Performance improves monotonically with data and model size, bringing RecSys closer to the broader LLM paradigm where scaling laws are a central design guide.

**4. Pre-training + post-training + reward alignment.** Instead of building each recommender from scratch, start from a pre-trained foundation and use task-specific post-training and reward alignment. Multiple use cases reuse the same foundation and infrastructure, rather than re-implementing capabilities in separate, siloed systems.

**5. RecSys infrastructure → LLM infrastructure.** The serving stack increasingly resembles modern LLM infrastructure — GPU-accelerated, vLLM/Triton-based, with careful batching and caching — rather than classic RecSys infrastructure built around MLPs or factorization models. KV-caching, prefix caching, and prefill-only inference become key levers.

**6. Recommendation steering via prompts.** LLM backbones enable flexible recommendation steering through natural-language inputs. Steering recommendations via prompts rather than re-designing specialized models and pipelines.

## What This Means for the Systems You Build

If you're building RAG systems or any pipeline that takes structured data and feeds it to an LLM, the context engineering lessons from GenRec apply directly. The verbalization strategy — retain high-signal events in full, omit low-signal noise, compress repetitive patterns, elaborate selectively on cold-start items — is exactly the strategy you should use for document context in RAG.

The context length optimization finding is concrete and actionable: you can likely cut your context to a third with negligible quality loss if you're selective about what goes in. Most RAG pipelines stuff the context window with every retrieved chunk. GenRec proves that selective, compressed context preserves quality while cutting inference cost proportionally.

The prefill-only inference pattern is worth understanding even if you're not building a recommendation system. Any time you need to score a large set of items against a single context (retrieval re-ranking, batch classification, multi-label scoring), a single forward pass beats autoregressive decoding by orders of magnitude in latency and cost.

## The AI-Era Connection

**Context engineering as the new feature engineering.** This is the central thesis. If you're building an LLM-backed system, the prompt is your feature vector. The quality of your system depends on what you include in the context, how you compress it, and how you structure it — not on engineering individual features or designing custom architectures.

**Reward-weighted training as cheap alignment.** Full RLHF is expensive. Reward-weighted ranking loss — just scaling the training loss by a reward signal — is simpler, more stable, and nearly as effective. If you need to align an LLM toward specific behaviors (long-term user value, content diversity, safety), reward-weighted loss is the pragmatic starting point before investing in full RL.

**Foundation model amortization.** Phase 1 is expensive and infrequent. Phase 2 is cheap and frequent. This is the pattern for any production LLM system: build a strong base once, then adapt cheaply and often. The marginal data efficiency at Phase 2 (40× less labeled data to match production quality) is the payoff of that investment.

**Prefill-only as a serving pattern.** Autoregressive decoding is expensive. If your task can be reformulated as "score all candidates in one forward pass" rather than "generate tokens one at a time," the cost difference is enormous. This applies to re-ranking in RAG, multi-label classification, and any scoring task over a known candidate set.

## How This Connects

The Spotify routing article above solves the same economic problem at a different layer: Spotify routes I/O to cheap models at the developer-tool level, GenRec routes inference to the right model size and context length at the infrastructure level. Both are cost optimization through intelligent routing — Spotify by work type, Netflix by model size and context compaction.

The next section on Netflix's LLM Judge Lifecycle connects to GenRec through a shared problem: GenRec needs quality guarantees for the recommendations it produces. The LLM judge lifecycle describes exactly how you build and maintain those quality guarantees at Netflix scale — not for the recommendations themselves, but for the natural-language explanations that accompany them.

## The Mentor's Honest Take

The mistake you will make: you will focus on the model architecture (catalog-aware scoring head, prefill-only inference) and miss the real lesson. GenRec's architecture is straightforward — it's a decoder-only transformer with a linear scoring head. The innovation is in the context engineering: what goes into the prompt, how it's compressed, and how the token budget is allocated across event types.

The non-obvious implication: the Phase-2 data efficiency (40× less labeled data than the production system) is not because LLMs are magical. It's because Phase 1 already invested in understanding users and content. The marginal data efficiency is the dividend of the foundation investment. If you skip the equivalent of Phase 1 and jump straight to fine-tuning an off-the-shelf model for your task, you'll need proportionally more labeled data. The 10-20% MRR gap between an off-the-shelf backbone and the Phase-1 foundation model makes this concrete — that gap is the value of domain-specific pre-training.

For someone building RAG systems: the context engineering strategy is the most directly transferable idea here. You're already doing a version of this when you decide what chunks to include in your context window. GenRec's contribution is showing that this decision is not a preprocessing step — it's the core modeling decision. Treat your context curation with the same rigor you'd treat feature engineering in a traditional ML pipeline. Measure the quality-cost curve as you vary context length. Find the elbow point. The paper shows it's at roughly a third of the naive context for recommendation, which is a useful starting hypothesis for your own experiments.

**Ranking: Useful context.** The context engineering and verbalization compaction findings are directly applicable to any LLM-backed system. The specific architecture (catalog-aware scoring head, reward-weighted loss) is Netflix-specific and won't transfer to your work, but the design patterns — foundation + post-training, context length as cost lever, prefill-only serving — are general. Not essential today, but essential knowledge when you scale.

# The Lifecycle of LLM-as-a-Judge — Building, Deploying, and Maintaining Quality Judges at Netflix Scale

---

## The Problem

Netflix generates hundreds of thousands of distinct show-level recommendation explanations per week. Each one is a short natural-language message explaining why a title was recommended — e.g., "A funny, heartfelt holiday romance about love and new beginnings, much like My Secret Santa." Each must be accurate, item-specific, and free of sensitive or offensive content. A misleading or poorly grounded explanation erodes the very trust the feature is meant to build.

Human evaluation is the gold standard, but at this volume it's not feasible. LLM-as-a-Judge is the standard scalable proxy — but most work treats a judge as a static artifact. Evaluate it once at construction or against a fixed benchmark, then deploy.

The problem: a judge operating in a deployed system is not static. The catalog shifts (new categories, seasonal content). The meaning of "high-quality" itself evolves. The recommendation algorithms upstream change. The user population changes. A judge that was well-aligned at deployment will not stay aligned.

Netflix treats the judge as a **lifelong agent** with a four-phase lifecycle: Birth → Training → Deployment → Monitoring. Each phase poses distinct technical and operational challenges, and the loop never closes — Phase IV feeds back into Phase II continuously.

## The Mechanism

### Phase I: Birth — Establishing Ground Truth

This is the most human-intensive phase. Internal writing experts define the evaluation criteria, author labeling guidelines for human raters, hand-craft adversarial examples, and anchor human rating. The guidelines double as the seed rubrics for the LLM judges optimized in Phase II. Every fail label carries a free-text rationale against the guideline.

The benchmark draws on three complementary sources:

1. **Expert-crafted examples** — each with a human rater's pass/fail label, its known failure mode, and a rationale for failure. Covers cases the other two sources can't reliably produce.
2. **Human-rated, LLM-synthesized examples near the criterion boundary** — captures difficult cases that naturalistic sampling rarely surfaces.
3. **Sampled explanations from the generation system** — collected before full pipeline integration.

At the start of online experiments, the benchmark held roughly **900 human-labeled explanations**, split close to evenly between labels with a slight majority of FAIL (~54%). They deliberately hold classes near balance rather than matching prevalence in generated samples (where failures are far rarer), because alignment metrics depend on human-failed examples.

The criteria split into **must-have pass/fail conditions** (every explanation must satisfy before being shown) and **softer stylistic and recommendation-relevance criteria** (specific criteria are withheld for confidentiality).

Public LLM-judge benchmarks (JudgeBench, RewardBench) target general-purpose evaluation and miss the constraints of recommendation explanations, which are item-specific, context-dependent, and short. Hence the domain-specific benchmark.

The dataset is not fixed. The Phase IV HITL pipeline appends ~300 freshly rated explanations each week, tracking distribution shift in the live catalog.

### Phase II: Training — Reasoning-Aligned Rubric Tuning (RART)

One judge is tuned per must-have criterion (three in total). Each judge is instantiated from a small, task-invariant prompt template: a fixed system message describes the evaluation task with a templated `<criterion>` slot holding the rubric being tuned; a user message supplies the explanation text and item metadata. The judge emits a JSON object `{label, reason}` per explanation.

Tuning reduces to refining the criterion rubrics while the surrounding prompt is held constant.

**The RART loop (Algorithm 1):**

Given a rubric R_t at iteration t:

1. Score the training and validation sets with the current judge J(R_t) — each example gets a (label, rationale) pair
2. Compute weighted alignment metrics on validation
3. If metrics improve, save current rubric as best
4. If all metrics clear per-criterion bounds, stop early
5. Identify the **focus set** — two types of errors:
   - **Label mismatches:** examples where the judge and human disagree on pass/fail
   - **Agreed-fail but wrong reason:** examples where both the judge and human say FAIL, but the judge's rationale doesn't match the human rationale (detected by a meta-judge M)
6. A **reflector LLM** proposes a refined rubric from the focus set
7. Repeat

The critical insight: an "error" is not only a wrong label. The meta-judge M compares the judge's free-text reason against the human rationale on agreed-fail examples. **Right verdict, wrong reason** is also an error — because in Phase III, the judge's rejection reason becomes the generator's revision instruction. A misleading reason propagates downstream.

**Three alignment metrics:**

**Specificity (fail-recall):** The judge's rate of correctly rejecting bad explanations. The most critical metric — a bad explanation that slips past the gate directly erodes member trust.

```
Spec = |{x: judge=FAIL, human=FAIL}| / |{x: human=FAIL}|
```

**Recall (pass-recall):** Rate of correctly passing good explanations. High recall keeps explanation coverage high and revision cost low.

```
Rec = |{x: judge=PASS, human=PASS}| / |{x: human=PASS}|
```

**Reasoning agreement rate (RAneg):** Fraction of human-failed examples where the judge and human both reject the explanation *and* agree on why it fails. Denominator is all human-fail examples (not just agreed-fail), since reasoning can only agree where both labels are FAIL.

```
RAneg = |{x ∈ agreed-fail : meta-judge says AGREE}| / |{x: human=FAIL}|
```

The optimization score collapses these into a single weighted score:

```
s = w_s · Spec + w_r · Rec + w_ra · RAneg
```

With w_s = 3 and w_r = w_ra = 1 — specificity is weighted 3× higher because the two error types are not symmetric online. A bad explanation that escapes gating is served to members, whereas a good one that is rejected is only revised or dropped.

**Validating the meta-judge M:** Trained raters independently labeled rationale agreement on 300 agreed-fail rationale pairs. M's verdicts matched human judgments **98.6%** of the time, supporting its use as both metric and learning signal.

**RART vs. Vanilla (label-only reflection):** Across 8 seeds per criterion on held-out test sets:

- **Criterion 1:** RART improves specificity more than vanilla, with a recall cost that's acceptable because rejected explanations re-enter the revision loop
- **Criterion 2:** Default rubric already near ceiling — both methods indistinguishable
- **Criterion 3:** Vanilla collapsed specificity and reasoning agreement in every iteration (best-checkpoint rule returned essentially the default rubric, lift ≈ 0). RART lifts both metrics and even improves recall slightly

Reasoning alignment helps where there is room and does not hurt where there is none. The headroom the default rubric leaves governs how much RART can gain.

### Phase III: Deployment — Two Roles for One Judge

The tuned judge serves two online roles on every generated explanation:

**Role 1 — Gate.** Rejects explanations failing a configurable subset of criteria. Pass → serve to members. Fail → enters the revision loop.

**Role 2 — Critic in a self-reflective revision loop.** Returns flagged explanations to the generator with the judge's reason appended to the prompt. The generator re-drafts, up to K retries. An explanation still failing after K attempts is **dropped** — not served.

Dropping rather than serving is a deliberate asymmetry. A bad explanation is a trust hazard. A missing one merely forgoes an opportunity.

Explanations are generated per recommended item, not per (user, item) pair. An online personalization model then selects the best-fitting explanation for each pair — so a single explanation can be shared across many users.

**Cumulative pass rate vs. revision budget:** Across n=1000 generated explanations and four generator models, pass rate rises monotonically with retries (the judge's free-text reason steers each next draft), but returns diminish fast. The three strong generators capture **≥80% of achievable lift by k=3-4**. Revision only partly rescues weak generators (model 3 stays below 50% even at k=12). A sustained drop in the k=0 pass rate signals a generator-side regression rather than judge drift.

Netflix deploys K=3 with the strongest generator model. At this budget, the end-to-end pipeline runs at a few thousand US dollars per week in inference cost.

**Key design insight:** Judge-guided revision amplifies a capable generator rather than substituting for one.

### Online A/B Test

Five-week test on the mobile surface, comparing judge-aligned explanation pipeline against a no-explanation control over tens of millions of members.

- Viewing shifted toward **novel content** (titles the member had not previously watched): **+0.2% relative** (p < 0.05)
- **Successful browse-to-play sessions** increased: **+0.3% relative** (p < 0.05)
- Zero user-initiated escalations related to explanation quality

These relative lifts are small in absolute value but at Netflix scale correspond to substantial aggregate effects. Judge-aligned explanations are not just quality-compliant but also useful.

### Phase IV: Monitoring — Keeping the Judge Aligned

**Weekly HITL sampling:** ~300 explanations drawn from the generated pool each week, stratified across the judge's decision outcomes (served without revision, served after revision, dropped) and biased toward newer catalog items where drift is most likely. Stratification is fixed week to week for comparability. Each explanation is reviewed by at least 3 raters, majority label is ground truth.

**Drift detection:** For each alignment metric M, score the judge and each individual rater against the same majority label on the same weekly sample. This yields one value M(J) for the judge and a set of per-rater values. The requirement:

```
M(J) ≥ mean(M(H)) − 2·sd(M(H))
```

The judge must score no worse than two standard deviations below the average rater, where the standard deviation measures disagreement among the raters themselves.

This is **not a fixed threshold.** A harder weekly sample raises human disagreement, widening sd and with it the acceptance band. The judge is not penalized for difficulty that humans also find hard. The criterion is applied both to the full weekly sample and separately to newly added titles, where catalog shift appears first.

**A drift event triggers Phase II re-tuning** on the augmented benchmark, with the new rubric staged behind a manual review gate before deployment. The previous rubric is retained for rollback.

During the full A/B test, the judge stayed within the human band on every metric, including newly added titles — no re-tuning was triggered. But the loop still matters going forward because catalog, algorithms, and users keep changing.

**Qualitative failure patterns surfaced by weekly review:**
- Borderline cases where pass/fail depends on how confidently the explanation is phrased rather than underlying recommendation quality
- Genre-specific issues — stand-up comparisons where two specials share surface-level tags but sit in very different cultural contexts
- Explanations passing every must-have criterion yet reading as confusing or oddly framed

None of these necessarily move the alignment metrics, but each calls for rubric revisions. When a pattern recurs, writing experts revise the labeling guidelines, and affected judges are re-tuned. Because those guidelines are source of truth for both raters and judges' seed rubrics, one revision updates both sides.

Continuous review surfaces the qualitative, long-tail issues that quantitative drift detection is blind to — catching emerging gaps in the rubric itself, not just degradation relative to it.

### Takeaways from Operating at Scale

Three lessons Netflix expects to transfer:

1. **Invest in the benchmark before the judge.** A modest, rationale-annotated benchmark is worth more than a large label-only one, because rationales are what make reasoning-aligned tuning possible.
2. **One tuned judge can serve many roles.** Reusing it for gating and generation critique reduces alignment cost and keeps online behavior consistent.
3. **Plan monitoring from day one.** A recommender platform's items and users constantly evolve. LLM judges, like any lifelong agent, must be monitored and re-tuned.

### Limitations

- Evaluation comes from controlled experiments over months, not continuous operation — they can't confirm behavior across year-scale shifts
- A/B test covers one surface (mobile) and one explanation family (similarity-based) — lift may not transfer elsewhere
- RART is validated against label-only ablation but not against general-purpose textual optimizers (GEPA, TextGrad)
- Drift-triggered re-tuning has not yet fired online — automated response validated only offline

### Future Directions

Four extensions of RART:

1. **Rubric tuning as memory management** — benchmark too large for one reflection pass consumed in chunks, with the tuner consolidating reasoning from earlier chunks into a persistent scratchpad. New Phase IV rationales update the scratchpad incrementally instead of full re-tune.
2. **Reasoning-finetuning the judge** on accumulated rationales while text-space rubric optimization handles online adaptation.
3. **RART as reflective prompt evolution** (GEPA-style Pareto pool trading off the three metrics directly, rather than greedy single-objective).
4. **Promoting the judge from evaluator to reward model** — a rubric-tuned judge already emits (reason, label), the shape a reasoning reward model needs. The same artifacts could post-train the generator. The asymmetry of the alignment metrics suggests a constrained objective: hold each must-have criterion at its operating point as a constraint while optimizing softer criteria, instead of fixing the tradeoff through weights.

## What This Means for the Systems You Build

If you use LLM-as-a-Judge anywhere — eval pipelines, content moderation, faithfulness verification in RAG — this paper describes what happens after you deploy the judge. Most teams stop at "validate against a golden set, ship if accuracy is sufficient." Netflix's contribution is showing that the lifecycle continues: the judge drifts, the data drifts, and you need a loop to detect and correct both.

The reasoning alignment finding is the most transferable insight. Label agreement between judge and human is necessary but not sufficient. A judge that rejects an explanation for the wrong reason will give the generator a misleading revision instruction. In your RAG pipeline, if a grounding judge rejects an answer as "not supported by the documents" when the real issue is factual incorrectness, the generator will try to make the answer more grounded rather than more accurate. Right verdict, wrong reason → wrong fix downstream.

The drift detection approach (judge must score within 2σ of human raters, threshold is adaptive to sample difficulty) is a concrete, deployable pattern. You don't need Netflix scale to use it. Sample ~300 items per week from your judge's decisions, have humans label them, compare.

# Synthesis — LLM Systems Economics: The Complete Picture

## The Story in One Paragraph

Building production LLM systems that are both high-quality and cost-sustainable requires engineering three tightly connected layers that most teams address in isolation: routing (deciding which model handles which work — Spotify saves 90% of frontier token costs by routing I/O to cheap models via declarative modes and enforced hooks), context engineering (deciding what information enters the model's context window and how — Netflix reduces GenRec's serving cost to a third by compacting verbalized user histories from 5,000 to 1,700 tokens with negligible quality loss), and quality verification as a lifecycle (LLM judges that gate output quality are themselves LLM systems that drift — Netflix's RART-based lifecycle with weekly human-in-the-loop monitoring and adaptive drift thresholds keeps judges aligned with humans over time, not just at deployment). The connecting insight: the model is the easiest component to swap. The routing infrastructure, context engineering strategy, and verification lifecycle are the durable investments that determine whether the system works at scale and stays working.

## The Ranking

### Essential

- **Model Routing for Token Economics (Spotify).** If you're paying for frontier tokens in any agentic or RAG workflow, routing I/O to cheap models is the highest-ROI intervention. The implementation is simple, the savings are immediate (90% on bulk reads), and the principle (route by work type: I/O vs. judgment) applies everywhere.

- **LLM Judge Lifecycle (Netflix).** If you use LLM-as-a-Judge anywhere — eval pipelines, content gating, faithfulness checks — the lifecycle framing changes how you operate. Judges drift. Right-verdict-wrong-reason is as dangerous as wrong-verdict. Weekly monitoring with adaptive thresholds is operational hygiene, not research.

### Useful Context

- **LLM-Backed Recommendation Ranking (Netflix GenRec).** The context engineering and verbalization compaction findings transfer directly to RAG and any LLM-backed pipeline. The specific architecture (catalog-aware scoring head, prefill-only inference) is Netflix-specific, but the design patterns — foundation + post-training, context length as cost lever, reward-weighted alignment — are general. Essential knowledge when you scale, useful context today.

## The Most Expensive Mistakes

1. **Feeding all work to the frontier model.** Every token of file reading, boilerplate generation, and document extraction goes to the most expensive model. *Fix:* Route by work type. I/O goes to cheap models. Reasoning stays on the frontier model. Enforce routing with hooks or gates, not advisory instructions.

2. **Stuffing the full context window.** Every retrieved chunk, every historical event, every metadata field crammed into the prompt. *Fix:* Apply GenRec's verbalization compaction strategy — retain high-signal content, omit noise, compress repetition. Find the quality-cost elbow point experimentally. Netflix cut context to a third with negligible quality loss.

3. **Treating the LLM judge as a one-time build.** Validate against a golden set, ship, never revisit. *Fix:* Implement Phase IV monitoring — ~300 human-labeled samples per week, compare judge to human raters, use adaptive drift threshold. When the judge drops below 2σ of rater agreement, re-tune.

4. **Ignoring right-verdict-wrong-reason.** The judge correctly rejects an output but gives the wrong reason. In a revision loop, the wrong reason becomes a misleading instruction. *Fix:* Use a reasoning meta-judge (Netflix's matched human rationale judgments 98.6% of the time) to detect agreed-fail-but-wrong-reason cases. Include them in the focus set for rubric refinement.

5. **Advisory routing instructions that the agent ignores.** Routing rules in a markdown file that the agent can and will bypass. *Fix:* Hook-based enforcement that blocks the expensive operation before it happens. The agent doesn't get a choice — the hook fires before the tool call.

## The Cross-Cutting Pattern

All three sources converge on the same structural insight: **the model is the most commoditized, most replaceable component in the system.** Spotify's routing works with any worker model — swap Gemini Flash for something cheaper and the plugin doesn't change. GenRec's foundation backbone gets upgraded at low cadence while Phase 2 adapts cheaply. The LLM judge lifecycle explicitly plans for model changes by monitoring alignment continuously rather than assuming it.

The corollary: your engineering investment should flow toward the durable infrastructure. Routing logic, context engineering pipelines, quality verification loops, and drift monitoring — these persist across every model upgrade. Optimizing for one specific model's quirks is the most fragile investment you can make.

A second pattern: **cost optimization and quality optimization are the same engineering problem.** Shorter context → less cost and better attention. Routing I/O away from the frontier model → less cost and often better results (the cheap model's focused summary beats the frontier model's diluted attention on a massive file). The judge lifecycle → maintained quality that would otherwise silently degrade. In each case, the "cheaper" approach is also the "better" approach, not a tradeoff.

## Where This Goes Next

**Established fact:** Model routing, context engineering, and LLM-as-a-Judge are already production infrastructure at Spotify, Netflix, and other large platforms. These are not speculative — they're deployed and measured.

**Near-term (3-6 months):** Expect routing to become a standard feature of AI coding tools rather than a plugin. Context compaction strategies will be automated — models will learn what to include rather than relying on handcrafted verbalization rules. Judge lifecycle management will move from research paper to operational checklist as more teams hit drift in production.

**Informed prediction (6-12 months):** The gap between "LLM demo" and "LLM product" will be defined by these three layers — routing, context engineering, and verification lifecycle. Teams that built the infrastructure early compound advantages as models improve (because the infrastructure persists). Teams that optimized for a specific model version reset to zero on every upgrade. GenRec's data showing that Phase-2 efficiency improves with a better Phase-1 foundation is the clearest evidence of this compounding.

## The Single Most Important Thing

The model handles judgment — everything else should be routed to cheaper compute, compressed to fit the token budget, or verified by a judge that you monitor and re-align every week, not every quarter.
