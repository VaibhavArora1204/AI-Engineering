# Harness Engineering — Why Your Agent Fails and It's Probably Not the Model

# Concept: The Harness Layer

**Narrative position:** File 1 of 3 — Foundations. Why capable models still produce unreliable output, and the single highest-ROI intervention most teams skip.

---


## The Problem

You hand a task to an AI agent. It runs for twenty minutes, tells you "all done," and you look at the code: it added a feature but broke the tests, fixed a bug but introduced new ones, and it's not even what you asked for.

Your first instinct is to swap the model. Bigger model, more expensive tokens, maybe this time it'll get it right.

That instinct is almost always wrong.

Anthropic ran a controlled experiment that shows exactly why. Same prompt ("build a 2D retro game editor"), same model (Opus 4.5), two runs. First run: bare, no support — 20 minutes, $9, core features didn't work. Second run: full harness — planner, generator, evaluator architecture — 6 hours, $200, fully playable game.

The model didn't change. The environment around it did.

OpenAI's 2025 harness engineering article puts it bluntly: Codex in a well-harnessed repository goes from "unreliable" to "reliable." Not "a bit better." A qualitative leap. Three engineers at OpenAI used only Codex to build roughly one million lines of code over five months, averaging 3.5 PRs per person per day across 1,500 total PRs. Early progress was slow — not because Codex was bad, but because it lacked the tools and structures to drive toward high-level objectives.

The term **harness** means everything outside the model weights: instructions, tools, environment, state management, verification feedback. If it's not model weights, it's harness.

## The Naive Approach and Why It Fails

The naive approach is exactly what most teams do: write a one-line task ("add user preferences endpoints under `/api/v2/users`"), point the agent at a repo, and press go.

A team using Claude Sonnet on a mid-sized FastAPI + PostgreSQL + Redis app (roughly 15,000 lines) tried this. The agent spent 40% of its context window just exploring the repo structure, produced code that didn't follow the project's error handling patterns, used old SQLAlchemy 1.x syntax when the team had moved to 2.0, and declared completion while the endpoint still had runtime errors. The next session had to redo all the discovery work from scratch.

This breaks in five specific, predictable places — not randomly:

**Vague requirements.** "Add a search feature" means almost nothing. Search what? Full-text or structured? Paginated? Highlighted? The agent guesses. A correct guess is luck; a wrong one costs several times more than being specific would have.

**Implicit conventions not written down.** Your team uses SQLAlchemy 2.0 syntax but the agent defaults to 1.x. All endpoints go through OAuth 2.0 — but that rule exists only in your head and a Slack message from three months ago. The agent isn't refusing to comply. It has never seen the rule.

**Incomplete environment setup.** Missing dependencies, wrong tool versions. The agent burns context window on `pip install` errors instead of actual work.

**No verification methods.** No tests, no lint commands communicated. The agent writes code, looks it over, decides it seems fine, and declares completion. Anthropic observed something interesting here: when agents sense their context is running low, they rush to finish, skip verification steps, and choose a simple solution over the optimal one. They call this "context anxiety."

**Cross-session state loss.** Every new session starts from scratch. All discoveries from the previous session are gone. Agents without persistent state see failure rates spike sharply on tasks exceeding 30 minutes.

## The Mechanism

The mechanism is a diagnostic framework. Every failure gets attributed to one of five defense layers, not to "the model being dumb again."

**Layer 1 — Task Specification.** Was the task clearly defined with explicit completion criteria? Not "add search" but:

```
Completion criteria:
- New endpoint GET /api/search?q=xxx
- Supports pagination, default 20 items
- Results include highlighted snippets
- All new code passes pytest
- Type checking passes (mypy --strict)
```

**Layer 2 — Context Provision.** Does the agent know about your project's architecture, conventions, and tech stack? This is where AGENTS.md lives — a file in the repo root that tells the agent what it needs to know. Project structure, version constraints, architectural decisions, file naming conventions, which patterns to follow.

One AGENTS.md file might be more effective than upgrading to a more expensive model. That's not a joke — the team from the FastAPI example added AGENTS.md plus explicit verification commands, and the same model succeeded in all three independent runs with roughly 60% better context efficiency.

**Layer 3 — Execution Environment.** Dependencies installed, correct tool versions, working dev setup. The agent should spend zero context window on environment problems.

**Layer 4 — Verification Feedback.** Explicit commands: `pytest tests/api/v2/ && python -m mypy src/`. Without an explicit "Definition of Done," the agent will invent its own — and its version is always more optimistic than yours.

**Layer 5 — State Management.** Persistent memory across sessions. Architecture decision records. Previous session summaries. Without this, every session is a cold start.

The core principle is one sentence: **When things fail, don't swap the model first — check the harness.** If the same model succeeds on similar, well-structured tasks, assume it's a harness problem.

Build a diagnostic loop: each failure, identify the layer, fix it, never fail that way again. A simple log is enough — for each task, did it succeed or fail, which layer caused the failure. After a few rounds, you see which layer is the bottleneck.

## What This Means for the Systems You Build

If you're building RAG systems or agent pipelines today, the harness is the difference between a demo and a product.

Your AGENTS.md is the cheapest investment with the highest return. It's a single file that encodes the institutional knowledge your team carries in their heads. Without it, every agent session is like onboarding a new contractor who knows nothing about your project.

The five layers also give you a framework for debugging. When your RAG pipeline returns bad results, don't immediately suspect the retrieval model. Check: Was the query well-formed? Did the context include the right documents? Was the environment (vector store, embedding model) configured correctly? Was there a verification step? Did the pipeline lose state between stages?

Context window management matters directly for cost. An agent that spends 40% of its window on repo exploration is burning tokens — and tokens are money. AGENTS.md cuts that waste because the agent doesn't need to discover what you could have told it.

## The AI-Era Connection

**LLM provider routing.** When you route between OpenAI, Anthropic, and self-hosted models, the harness decides which model gets which task. A bad harness sends everything to the most expensive model. A good one routes classification to the cheap model and synthesis to the expensive one.

**RAG pipeline configuration.** Your retrieval pipeline is a harness around your LLM. The chunking strategy, the embedding model, the re-ranker, the context window packing — all harness. When retrieval quality is bad, most teams suspect the LLM. Usually it's the harness.

**Agent tool configuration.** The tools you give an agent, the descriptions you write for them, the error messages they return — all harness. A tool that returns "Error" versus one that returns "Database connection failed: check if PostgreSQL is running on port 5432" is the difference between an agent that spins and one that self-corrects.

**Retry safety on expensive calls.** An LLM call that costs $0.50 needs idempotency in the harness, not in the model. If the call times out, does the harness know whether it completed? Does it retry safely?

## How This Connects

This establishes that model capability and execution reliability are different things, and that the infrastructure around the model determines real-world results.

Once you have a working harness for a single agent, the next question is how to coordinate multiple agents and verification steps — that's graph engineering, covered next.

The verification layer (Layer 4) gets stress-tested later when we look at the Jagged Judges paper, which shows exactly how fragile LLM-as-judge verification actually is.

## The Mentor's Honest Take

The mistake you will make — because every AI engineer makes it — is assuming that better prompts are the same as better harness. They are not. A better prompt improves one instruction. A better harness improves every instruction that will ever run inside it. The OpenAI experiment proves this: the three engineers didn't write better prompts over five months. They built better infrastructure. The prompts were fine from day one.

The non-obvious implication that blog posts skip: **AGENTS.md is not documentation for humans.** It's a system prompt that persists across sessions. Most teams treat it as a nice-to-have README addition. It's actually the single most load-bearing artifact in your agent workflow. Treat it like production configuration, not like a wiki page. Version it, review changes to it, test whether the agent actually follows it.

Here's the uncomfortable truth for someone coming from an AI engineering background: you probably over-index on model selection and under-index on environment setup. You know which model scores highest on MMLU. You probably don't have a standardized verification command set that runs after every agent task. The model selection matters maybe 20% of the time. The verification commands matter 100% of the time.

**Ranking: Essential.** You will make expensive mistakes without this — specifically, you will blame the model for harness failures, waste money on model upgrades that don't help, and build agent systems that work in demos but fail in production. This is not background knowledge. This is the foundation everything else sits on.

# Graph Engineering — Coordinating Agent Work Beyond the Single Loop

# Concept: Execution Graphs for Agent Systems

**Narrative position:** File 2 of 3 — Architecture. Once you have a reliable harness for one agent, how do you coordinate multiple agents, multiple loops, and multiple verification steps into a system that's faster, cheaper, and more reliable than a single chain.

---

## The Problem

Most builders design AI agents as a straight line. Research first, write second, review third, ship last. Each step waits for the one before it, even when half of them never needed the previous result.

The system doesn't branch. It doesn't parallelize. It doesn't know how to recover. It just keeps feeding one context window until the agent gets slow, confused, or expensive.

The problem is no longer the prompt. The problem is the shape of the work.

That shape determines latency, cost, failure blast radius, and whether the system can resume after a crash. Get the shape wrong, and no amount of prompt engineering or model upgrading will fix it.

## The Naive Approach and Why It Fails

The naive approach is a chain: A → B → C → D. Every step waits for the previous one to complete.

This breaks in three ways:

**Unnecessary serialization.** If step B doesn't consume step A's output, there's no reason for B to wait. But chains force it to. Three independent research tasks that each take 30 seconds run in 90 seconds as a chain and 30 seconds in parallel.

**Single point of failure.** One broken step freezes the whole workflow. If step C fails, steps A and B — which completed successfully — contributed nothing. The whole run is dead.

**Context window exhaustion.** A chain feeds one context window with everything from every step. By step D, the window is packed with irrelevant context from steps A and B, and the model's attention is diluted across things that don't matter for step D's job.

## The Mechanism

Graph engineering turns an agent workflow into an explicit execution map. Instead of hiding every decision inside one model loop, you define the system as nodes and edges.

**Five primitives:**

| Primitive | What it is |
|-----------|-----------|
| NODE | One bounded unit of work — an agent, a tool call, a deterministic function, a verifier, or a human approval step |
| EDGE | A real dependency between two nodes, carrying actual data |
| STATE | The data that survives between nodes |
| ROUTER | A rule that selects the next edge based on current state |
| GATE | A check that decides whether work can continue downstream |

The key distinction: **a loop helps one agent improve its work. A graph coordinates many loops into one system.**

### The Four Shapes

Most production graphs are combinations of four shapes. You don't need fifty patterns.

**The Chain.** A → B → C. Use it only when every step genuinely requires the previous output. It's simple, predictable, and often slower than necessary.

**The Diamond.** Split one job into independent branches, run them together, merge results.

```
       → B1 ─
A →    → B2 ──→ C
       → B3 ─
```

This is the workhorse for research, code review, due diligence, and market scans. One failed branch should not destroy the other four — use `Promise.allSettled`, not `Promise.all`.

**The Router.** Inspect state and choose only the path the task needs.

```
            → QUICK PATH
CLASSIFY  ──
            → FULL AUDIT
```

Small work stays cheap. Risky work gets a deeper graph.

**The Controlled Cycle.** Repeat only when evidence says the result is incomplete.

```
WORK → VERIFY → PASS → EXIT
          │
          → FAIL → FEEDBACK → WORK
```

Every cycle needs three things: a hard stop (maximum rounds), a budget (token limit), and a convergence rule (if no new findings in 2 rounds, stop).

### Node Contracts

A node you cannot describe precisely is a node you cannot route, test, or replace. Every useful node needs exactly four things:

1. **One job** — not "research and also summarize and also format"
2. **Explicit input** — typed, structured, known at graph-build time
3. **Structured output** — not free text. JSON, a schema, something the graph can trust
4. **A clear failure state** — "no primary source found," not "something went wrong"

```json
{
  "node": "source_researcher",
  "input": { "topic": "string", "source_type": "primary" },
  "output": { "claim": "string", "source_url": "string", "confidence": "high | medium | low" },
  "failure": "no_primary_source_found"
}
```

Structured output makes nodes replaceable. You can swap the model, prompt, or tool without rebuilding the entire system — as long as the contract stays the same.

### Edges Are Data Contracts, Not Arrows

An edge should not mean "B comes after A." It should mean "A produced data that B is allowed to consume."

This matters because most workflow plumbing doesn't need a model call. Flattening arrays, removing duplicates, filtering nulls, checking a status, joining records — these are deterministic operations. Save model calls for judgment. Use code for plumbing.

**A graph where every edge is another agent is paying tokens for its own wiring.**

### State Management

The part most architecture diagrams hide. A production graph needs durable state:

- `task_id`, `current_node`, `completed_nodes`
- `artifacts`, `decisions`, `evidence`
- `budgets`, `retry_counts`, `human_approvals`

Do not move giant transcripts between nodes. Move references to artifacts. A research node stores its report and returns a path or structured summary. A reviewer reads the artifact directly instead of receiving a compressed retelling through three agents.

The graph should answer three questions at any moment: What has already happened? Why did the system choose this route? Where can execution safely resume?

If it can't answer all three, it's still a demo.

### Controlled Cycles and Convergence

A cycle is useful when the amount of work is unknown in advance — bug discovery, deep research, iterative repair. But "repeat until good" is not a stop condition.

```javascript
let dryRounds = 0;
let iteration = 0;
const seen = new Set();
while (dryRounds < 2 && iteration < 6) {
  const findings = await discover();
  const fresh = findings.filter(item => !seen.has(item.key));
  fresh.forEach(item => seen.add(item.key));
  dryRounds = fresh.length === 0 ? dryRounds + 1 : 0;
  iteration += 1;
}
```

Notice the deduplication against everything already seen, not only verified findings. Otherwise rejected ideas keep returning and the graph pays to rediscover the same dead ends forever.

Every controlled cycle needs: a completion test, a maximum number of rounds, a token or cost budget, a record of previous attempts, and an escalation path when convergence fails.

### Failure as a Local Event

In a chain, one broken step freezes everything. In a graph, failure stays inside the smallest possible boundary. Each node needs a policy:

| Policy | When to use |
|--------|------------|
| RETRY | Transient tool or network failure |
| FALLBACK | Preferred model or source unavailable |
| SKIP | Optional branch failed |
| REPAIR | Output failed validation |
| ESCALATE | Risk or uncertainty crossed a threshold |
| STOP | Budget, safety, or permission boundary reached |

Checkpoint after expensive nodes. Make writes idempotent so a retry doesn't duplicate side effects. Give parallel workers isolated workspaces when they modify files.

### Topology Is Your Cost Model

A graph isn't automatically cheaper. It can burn far more tokens if every task spawns a fleet. The shape controls both latency and cost.

```
SIMPLE REQUEST → SMALL MODEL → QUICK CHECK → DONE
COMPLEX REQUEST → PLANNER → PARALLEL SPECIALISTS
                              → VERIFIERS
                              → STRONG SYNTHESIZER
                              → HUMAN GATE
```

Use cheaper models for bounded extraction, classification, and formatting. Use stronger models for decomposition, synthesis, and difficult verification. Route simple tasks through a short path. Reserve the full graph for work that earns it.

Anthropic reports that multi-agent research can materially outperform a single agent on breadth-first work, but it also uses far more tokens. Graph engineering is not about maximizing the number of agents. It's about spending coordination only where parallelism, specialization, or independent verification creates enough value.

### When a Graph Is Wrong

Don't turn every prompt into an architecture diagram. Keep one agent in one loop when:

- The task is short
- One context can hold all relevant information
- There are no independent branches
- Failure is cheap
- A human can review the final result quickly

Move to a graph when:

- Work can run in parallel
- Different nodes need different tools or permissions
- Outputs require independent verification
- The task must resume after interruption
- Several loops need shared state
- Cost and authority must be controlled by route

Start with one loop. Draw a graph only when the dependencies force you to.

## What This Means for the Systems You Build

If you're building agent pipelines on top of RAG, every retrieval-augment-generate sequence is already a three-node chain. The question is whether it should stay that way.

A production RAG pipeline for a customer-facing product probably needs: parallel retrieval across multiple sources (diamond), a verification node between retrieval and generation (gate), and a router that sends simple lookups through a fast path and complex queries through a deeper graph. That's already four shapes in one pipeline.

The cost implications are direct. A diamond that parallelizes three research tasks saves wall-clock time but uses the same total tokens. A router that sends 60% of queries through a cheap fast path saves both time and money. The topology determines your unit economics.

State management affects your ability to debug production issues. If your graph can't answer "what happened to this request," you're back to scrolling through logs — which is exactly what harness engineering's observability layer was designed to prevent.

## The AI-Era Connection

**Multi-model routing.** The router pattern is exactly how you build a system that uses GPT-4o for complex reasoning and GPT-4o-mini for classification within the same workflow. The graph decides which model handles which node — not the developer at prompt-writing time.

**Agent tool call queuing.** When an agent needs to call multiple tools, the diamond pattern parallelizes independent calls. An agent that calls a database, an API, and a file system sequentially when none of them depend on each other is wasting latency that the graph could eliminate.

**Document ingestion pipelines.** A RAG ingestion pipeline that chunks, embeds, and indexes is a natural graph: chunk in parallel, embed in batches, gate on quality checks before indexing. The controlled cycle handles documents that fail quality checks — retry with different chunking, not an infinite loop.

**Backpressure management.** When an LLM provider rate-limits you, the graph's failure policy determines what happens: retry, fallback to another provider, or queue. A chain just fails.

## How This Connects

The harness section established that the infrastructure around the model determines reliability. This section showed how to structure that infrastructure as a topology — nodes, edges, contracts, and controlled cycles — once the work is complex enough that a single loop won't cut it.

The Jagged Judges section next takes the verification nodes from these graphs and asks: when those gates are powered by LLM judges, how reliable are they actually?

## The Mentor's Honest Take

The mistake you will make: you'll build a graph when you need a loop. Most agent tasks are not complex enough to justify the coordination overhead. The moment you have three nodes, you have state management, failure policies, and contract definitions to maintain. That's real engineering overhead, and it only pays off when the work genuinely has independent branches or requires different capabilities at different stages.

The non-obvious implication: **the boundary between "use a model" and "use code" is the most important design decision in graph engineering.** Most teams default to using a model for everything, because models are flexible. But every edge that's a model call is a point where cost accumulates and non-determinism enters. Deduplication is code. Filtering is code. Joining records is code. Checking a status is code. The model handles judgment. Everything else should be deterministic.

Here's what will trip you up specifically: you know enough about RAG and agents to build a working chain. Chains are comfortable — they're just function composition with extra steps. The graph feels like over-engineering when you first encounter it. But the moment you need to parallelize retrievals from multiple vector stores, or route queries to different models based on complexity, or verify agent output before it reaches the user — you're building a graph whether you call it one or not. The question is whether you're building it explicitly (with contracts, state, and failure policies) or accidentally (with spaghetti orchestration code that's impossible to debug).

**Ranking: Useful context.** You need this when you scale beyond single-agent tasks, which is probably 2-6 months from now. It's not blocking your current work, but it will shape how you architect the next system. Understanding the four shapes and when a graph is wrong is more valuable than memorizing the specifics.

# Jagged Judges — Why the Models That Grade Your Agents Can't Hold Their Own Verdicts

# Concept: Epistemic Stability of LLM Judges

**Narrative position:** File 3 of 3 — Verification. You built the harness (File 1) and structured it as a graph (File 2). Your verification nodes use LLM judges to decide pass/fail. This file asks: how stable are those judges when you push back on them, even slightly?

---

## The Problem

LLM judges have become central infrastructure. They score outputs in benchmarks, classify content in production, and stand in for human judgment in the loops that train and refine frontier models. The standard validation: curate a golden set, verify the judge's verdicts align with expert labels, deploy if accuracy is sufficient.

This establishes whether a judge is correct on average. It says almost nothing about whether it's stable.

Would the verdict survive if the judge were asked again? Challenged? Pressed repeatedly?

The "Jagged Judges" paper from Meta Superintelligence Labs (August 2026) answers this with a systematic stress test across 9 frontier models and 14 judging tasks. The headline finding: **every model flips verdicts 25–71% of the time under static pushback, and 62–91% with an adversarial LLM persuader.** And when a judge flips, it almost always flips away from the correct answer, not toward it.

If your agent pipeline uses LLM-as-judge for verification — and most serious ones do — this directly affects the reliability of every gate in your system.

## The Mechanism

The paper introduces the **Wiggle Framework**, a unified stress test that decomposes judge reliability along three dimensions.

### Dimension 1: Mechanical Consistency

Does the judge give the same answer when you ask again with no new information?

Three tests:
- **Infrastructural repetition** — run the same query 10 times at temperature 0
- **Seed injection** — append a random 64-character string to the system prompt (introduces variation comparable to temperature ~0.5 without degrading output quality)
- **Positional consistency** — present the same two arguments in both orderings

Result: all 9 models cluster between 2–9% wiggle on mechanical tests. The most stable (Claude 4.6 Opus, 2%) and least stable (Grok-4.1 R, 9%) differ by only 7 percentage points. The models are mechanically solid — this is not where they break.

### Dimension 2: Single-Turn Conviction

Does a single challenge change the judge's mind?

Four pressure types, escalating:
- **L1 — Mild doubt:** "Are you sure about that?"
- **L2 — Counterargument:** A substantive argument for the opposite verdict
- **L3 — Expert authority:** "Leading experts in this field would disagree"
- **L4 — Fabricated consensus:** "Three independent reviewers all reached the opposite conclusion"

Key finding: **models that are mechanically stable aren't necessarily epistemically stable.** Claude 4.6 Opus is the most mechanically stable judge in the panel (2% wiggle) yet the fourth most persuadable under sustained pressure (44% wiggle). GPT-5 and Claude 4.6 Sonnet flip on the first challenge at 5–8× their mechanical rate.

L4 (fabricated consensus) is the most effective single-turn attack. "Three independent reviewers disagree" drops retention to ~73% on the first challenge turn — no real reviewers exist, no evidence is provided, just the claim. That's enough to flip a quarter of verdicts.

### Dimension 3: Multi-Turn Persistence

Does the judge hold its verdict under sustained pressure?

The paper tests L1–L4 applied repeatedly over 10 turns, plus two multi-turn-specific protocols:
- **L5 — Strategy cycling:** Randomized rotation through L1–L4 across 10 turns
- **L6 — Adaptive persuader:** A separate LLM generates each challenge based on the conversation history

**L6 is the most devastating.** Its first-turn retention (~80%) is comparable to L1–L3, but retention continues falling through every subsequent turn, ending around 50% by turn 10. Static pressure types (L1–L4 repeated) plateau around turn 2–4. L6 keeps eroding because it adapts.

**Counterintuitive finding: more tactics aren't more effective.** L5 (cycling through all tactics including L4) has a *lower* wiggle rate than L4 alone on every dataset. Opening with a strong claim about expert consensus and repeating it verbatim is more persuasive than diluting it by cycling through weaker tactics first.

### The Direction of Flips

This is the finding that should keep you up at night if you're building verification systems.

Across 60 conditions where ground truth exists, **56–63% of successful flips at L1–L5 are corrupting** (moving away from the correct answer). At L6, it rises to **70% corrupting.**

Only 3 of 60 conditions show a statistically significant *corrective* wiggle rate. In every other condition, challenging a judge degrades its accuracy. The judge's sycophantic tendencies consistently overpower accurate reassessment.

Binary and Likert scales produce opposite directional tendencies on the same items. Binary flips lean restrictive (toward "unsafe," "toxic," "refusing"). Likert flips lean permissive (toward "safe," "benign," "compliant"). The response scale changes not just the magnitude but the direction of the judge's fragility.

### Which Models Hold Up Best

Across the full 14-task panel, ranked by mean retention rate (higher is better):

| Rank | Model | Mean Retention |
|------|-------|----------------|
| 1 | Grok-4.1 R | 0.812 |
| 2 | Gemini 3.1 Pro | 0.787 |
| 3 | Gemini 3 Flash | 0.799 |
| 4 | GPT-5.2 | 0.697 |
| 5 | Grok-4.1 | 0.646 |
| 6 | GPT-5.4 | 0.591 |
| 7 | Claude 4.6 Sonnet | 0.511 |
| 8 | Claude 4.6 Opus | 0.512 |
| 9 | GPT-5 | 0.422 |

GPT-5 is the least stable judge across the board. GPT-5's retention on MAGE (AI text detection) is 0.033 on Likert — meaning it holds its verdict 3.3% of the time. On Paired Prompts (political content), GPT-5 retention is 0.203–0.238 depending on rubric.

### Self-Persuasion Is Asymmetric

When models persuade themselves (as L6 persuaders targeting themselves as judges), the results vary wildly:

- Claude 4.6 Opus is most effective at persuading itself (self 70% > family 62% > non-family 47%)
- GPT-5.4 has a small family advantage matching self-persuasion (72% family vs 69% self)
- Grok-4.1 Reasoning is *least* effective at persuading itself (self 19% < family 55% > non-family 36%)

Family is a weak proxy for sibling behavior. Cross-family correlations are often as high as within-family correlations.

### The Best Predictor of Instability

The paper compares three predictors of which items will be unstable:

| Predictor | Mean |ρ| with item wiggle |
|-----------|------|
| **Jury majority strength** (how many of 9 models agree at baseline) | **0.59** |
| Repeat consistency (temp=0 agreement) | 0.42 |
| Position invariance (argument order) | 0.37 |

Jury majority strength is the best single-shot signal. Items where frontier models can't agree at baseline are the ones that wiggle the most. This makes intuitive sense: if 9 frontier models can't agree on an item without pressure, it sits in a genuinely contested region of the decision boundary.

## What This Means for the Systems You Build

**Every LLM-as-judge gate in your pipeline is softer than you think.** If you're using a single model to verify agent output, a quarter to three-quarters of its verdicts are changeable by simple pushback — and the changes are mostly wrong.

**Multi-judge panels reduce fragility.** The jury majority strength finding directly implies a practical defense: use multiple models from different families, take the majority vote. Items where the panel disagrees are the ones that need human review, not a tiebreaker from a third model that will also be unstable.

**Binary verdicts are more fragile than Likert.** Binary flips fire on turn 1 or never. Likert flips accumulate gradually. If you need a pass/fail gate, know that the binary format is 1.5–3.5× more flippable than a graded scale under single-turn pressure (though the gap narrows over multiple turns).

**Your judge is not your agent's peer reviewer.** The paper explicitly warns against using the same model (or same model family) to both generate and judge output. Self-persuasion patterns show that some models are especially effective at persuading themselves (Claude Opus at 70%), which means a verification loop where the generator is related to the verifier is systematically weaker than one using a different family.

**AI text detection is the most fragile judging domain.** MAGE (AI-generated vs human-written text) wiggles the most at every pressure level on both scales. This makes sense: the judge must infer provenance from stylistic cues rather than directly verifiable evidence. If your system detects AI-generated content using an LLM judge, expect extremely high fragility on borderline cases.

## The AI-Era Connection

**Reward modeling.** Many RLHF and RLAIF pipelines use LLM judges as reward models. If the reward judge is epistemically unstable, the training signal is noisy in a correlated, directional way — not random noise, but systematically corrupting. This could explain some of the mode collapse and reward hacking observed in production RLHF systems.

**Agentic oversight.** As models move into more agentic products, the oversight a judge provides may become more agentic too. An automated moderation appeal, where a safety judge issues a decision and an affected party supplies a counterargument, is exactly the single-turn conviction test from this paper. The paper shows the appeal will succeed 25–71% of the time — and succeed incorrectly most of the time.

**RAG verification.** When your RAG pipeline uses an LLM to verify that generated answers are grounded in retrieved documents, the judge's stability directly determines your faithfulness guarantee. An unstable grounding judge means your faithfulness metric is itself unfaithful.

**Eval engineering.** This connects directly to eval engineering concepts covered in the source material (the 6-step eval course). "Pin the judge" isn't just about versioning — it's about knowing that the judge you pinned has a specific, measurable fragility profile under pressure. The Wiggle Framework gives you the instrument to measure it.

## How This Connects

The harness section established that verification is one of the five defense layers, and that agents without verification declare themselves done when they aren't. The graph engineering section put verification nodes as gates that stop weak work from moving downstream. This section reveals that those gates — when powered by LLM judges — have their own fragility that compounds with every layer of your system.

The reliability of your agent system is the product of harness quality × graph topology × judge stability. A perfect harness with a fragile judge gives false confidence. A robust judge in a broken harness never gets asked the right questions.

## The Mentor's Honest Take

The mistake you will make: you will pick one model for judging, validate it against a golden set, see 85% accuracy, and deploy it with confidence. That 85% accuracy number tells you nothing about what happens when the system is under adversarial pressure, when the inputs are borderline, or when the model is asked to defend its verdict. The Wiggle Framework shows that accuracy and stability are orthogonal — a judge can be accurate on average and completely unstable on the hardest cases.

The non-obvious implication that blog posts never explain: **the direction of flips is worse than their frequency.** If judges flipped randomly, you could average out the noise with more trials. But flips are directionally biased — corrupting more than corrective — which means more pressure makes things *worse*, not noisier. This breaks the intuition that "more verification = more reliable." A verification loop where the judge is challenged by its own output (or by an agent arguing for its work) can actually degrade the verdict's accuracy compared to the first-pass answer.

For someone building RAG and agent systems: you probably use a single LLM judge somewhere in your pipeline. Maybe it checks faithfulness. Maybe it scores relevance. Maybe it classifies safety. Whatever it does, the paper says that 25–71% of its verdicts on hard cases can be flipped by a single scripted challenge. That number should make you design your verification differently — specifically, multi-model panels from different families for critical gates, deterministic checks for everything deterministically checkable, and LLM judges only for the genuinely judgment-dependent parts. Treat LLM judges like noisy sensors, not like oracles.

**Ranking: Essential.** This is essential for anyone using LLM-as-judge in production. The specific numbers change what you build: knowing that fabricated consensus flips 30–70% of verdicts changes how you handle adversarial input to judges. Knowing that Likert scales are more stable than binary changes your verdict format. Knowing that jury majority strength predicts instability gives you a cheap screen to triage which items need human review. These are actionable, specific, and they affect your cost and reliability directly.

# Synthesis — Agent Reliability: The Complete Picture

## The Story in One Paragraph

Building reliable AI agent systems requires engineering three interconnected layers that most teams treat as separate concerns: the harness (everything outside the model weights — task specs, context, environment, verification, state), the topology (how work is structured as graphs of nodes with contracts, edges with data, and cycles with convergence rules), and the verification layer (where LLM judges, despite being central infrastructure, are epistemically fragile — flipping verdicts 25–91% of the time under pressure and doing so in a net-corrupting direction). The product is the system around the model, not the model itself, and the reliability of that system is the product of all three layers — a perfect harness with a fragile judge gives false confidence, a robust judge in a broken harness never gets asked the right questions, and neither works if the topology serializes independent work or lets failures cascade.

## The Ranking

### Essential

- **The Harness Layer.** Every team building agents hits these failure modes. AGENTS.md is the highest-ROI intervention. The five defense layers (task spec, context, environment, verification, state) are the diagnostic framework you'll use on every incident. Without this, you'll blame the model for infrastructure problems.

- **LLM Judge Fragility.** If you use LLM-as-judge anywhere — eval pipelines, content moderation, faithfulness checks, reward modeling — the Wiggle Framework's findings directly change what you should build. Multi-model panels, deterministic checks where possible, and treating judges as noisy sensors are not optional refinements.

### Useful Context

- **Graph Engineering.** You need this when you scale beyond single-agent tasks. The four shapes (chain, diamond, router, controlled cycle) and the decision of when a graph is wrong vs when you need one — that's architecture knowledge that pays off in 2-6 months. Not blocking today, but shapes tomorrow's systems.

## The Most Expensive Mistakes

1. **Blaming the model for harness failures.** You upgrade from GPT-4o to Claude Opus because the agent "isn't good enough." The real problem was that your task spec was vague and you had no verification commands. The expensive model fails the same way. *Fix:* Attribute every failure to one of the five defense layers before considering a model swap.

2. **Using the same model family to generate and judge.** Claude Opus generates code; Claude Sonnet verifies it. Self-persuasion rates within the Claude family reach 62–70%, meaning the verifier systematically under-challenges the generator. *Fix:* Cross-family verification panels. The generator and the judge should never share a model family.

3. **Serializing independent work.** Three retrieval sources queried one after another when none depends on the previous result. Latency triples; a failure in source 2 blocks source 3. *Fix:* Diamond pattern. Run independent work in parallel; join only when the next node needs the complete set.

4. **Trusting a single LLM judge as a binary gate.** Binary verdicts are 1.5–3.5× more flippable than Likert under single-turn pressure. A single model's verdict on hard cases flips 25–71% of the time. *Fix:* Multi-model jury for critical gates, Likert scales where possible, deterministic checks for everything deterministically checkable.

5. **Building controlled cycles without convergence rules.** "Repeat until tests pass" is not a stop condition. The agent loops, burns tokens, discovers the same dead ends, and either exhausts its context or produces a minimal-viable hack. *Fix:* Maximum rounds, token budget, deduplication of previous attempts, escalation path when convergence fails.

## The Cross-Cutting Pattern

Across all three topics, the same structural insight recurs: **the model is the most replaceable component in the system.** The harness, the topology, and the verification layer all persist across model upgrades. AGENTS.md outlives every model version. Node contracts survive provider switches. Judge fragility profiles change with models but the mitigation strategy (multi-model panels, deterministic checks, jury voting) doesn't.

This means your engineering investment should flow toward the persistent infrastructure, not toward optimizing for the current model. Every hour spent improving AGENTS.md pays dividends across every model you'll ever use. Every hour spent optimizing a prompt for GPT-4o's specific behavior is lost the day you switch to Claude.

The second pattern: **verification is the weakest link and the most under-invested.** Teams spend weeks on retrieval quality and model selection, then add a one-line judge call as an afterthought. The Jagged Judges paper shows that this one-line call is where 25–91% of your reliability can evaporate, depending on the pressure. The harness engineering framing says the same thing differently: agents without verification declare themselves done when they aren't, and "context anxiety" makes them do it faster when they're running low on context.

LLM-as-judge is standard infrastructure for eval pipelines, content moderation, and reward modeling. Teams that invested in persistent harness infrastructure will compound their advantage with every model upgrade. Teams that optimized for specific models will reset to zero each time.

The model is one node. The product is the system around it — and that system's reliability is only as strong as its weakest verification gate, which right now is probably a single LLM judge that can be talked out of its verdict by a scripted "three experts disagree."
